## 우선 수정할 문제

### 1. [P1] 자기 프로필 수정으로 관리자 권한을 얻을 수 있음

- 근거: `src/app/api/auth/profile/route.js:167`, `:189`, `src/lib/roleUtils.js:40`, `src/lib/auth.js:78`.
- 자기 정보 수정 API가 임의의 `rank`를 저장하고, 권한 판정은 직급 문자열에 `admin`·`관리자` 등이 포함되는지 검사한다.
- 일반 직원이 자신의 직급을 `admin`으로 변경하면 다음 요청부터 관리자 판정을 받는다. 로컬에서 `isAdminRole({ is_admin: false, position: '', rank: 'admin' })`이 `true`임을 확인했다.
- 개선: 권한은 별도의 서버 관리 필드로 판단하고, 사용자가 수정할 수 있는 표시용 직급과 분리한다. 관리자 권한 변경은 별도 권한 검증을 거쳐야 한다.
- 회귀 검증: 일반 직원이 직급을 바꿔도 관리자 API는 계속 403을 반환해야 한다.

### 2. [P1] 사번 필터가 빈 배열이 되면 근태 조회 권한을 우회함

- 근거: `src/app/api/attendance/route.js:82`, `src/lib/supabaseDb.js:108`.
- `empNo=,`처럼 값은 있지만 유효한 사번은 없는 입력은 파싱 후 `[]`가 된다. 빈 배열의 `.some()`은 false여서 권한 검사를 통과하고, 최종 필터는 빈 문자열이 된다.
- DB 조회는 빈 문자열을 제한 없는 조회로 처리한다. 일반 직원도 전체 직원 근태를 조회하거나 과거 월의 공용 캐시를 반환받을 수 있다.
- 개선: 정규화 후 사번 목록이 비어 있으면 400/403으로 거부한다. 관리자 전체 조회와 조회 가능한 사번이 없는 상태를 명시적으로 구분한다.
- 로컬 확인: `requested=[]`, `unauthorized=false`, `empNoFilter=''`, `dbUnrestricted=true`.

### 3. [P1] 팀장의 부서 제한을 요청 본문으로 우회할 수 있음

- 근거: `src/app/api/attendance/overtime-rounds/route.js:31`, `src/lib/supabaseDb.js:1163`.
- 팀장 권한 검사가 요청자가 보내는 `employeeDept`를 신뢰하지만, 실제 저장 대상은 별도로 받은 `empNo`다.
- 다른 부서 직원의 사번과 본인 부서 이름을 함께 보내면 해당 직원의 초과근무 기간/차수를 변경할 수 있다. 저장 함수에도 부서 검사가 없다.
- 개선: 대상 사번으로 DB에서 실제 부서를 조회한 뒤 세션의 관리 범위와 비교한다.

### 4. [P1] 직원을 비활성화해도 접근 권한이 유지됨

- 근거: `src/app/api/admin/employees/route.js:153`, `src/lib/auth.js:71`.
- 직원 상태 변경은 `is_active`를 저장하지만, 일반 계정의 세션 검증은 해당 필드를 조회하거나 확인하지 않는다. 로그인 경로도 활성 직원으로 제한하지 않는다.
- 기존 프로필이 있는 비활성 직원은 앱 접근을 계속할 수 있으며, 관리자라면 관리자 권한도 유지된다. 마스터 계정의 직원 모드에만 활성 여부 검사가 있어 일반 계정을 보호하지 못한다.
- 개선: 공통 인증 단계에서 재직/활성 상태를 강제하고, 시스템 계정 예외를 명시한다. 상태 변경 후 기존 세션으로 요청해도 거부되는지 검증한다.

## 안정성과 데이터 정확성

### 5. [P2] 늦게 도착한 응답이 현재 월/직원 데이터를 덮어씀

- 근거: `src/hooks/useDashboardData.js:162`, `:186`.
- 월 또는 직원 변경으로 요청이 겹쳐도 이전 요청을 취소하거나 최신 요청인지 확인하지 않고 공용 `monthlyData`에 저장한다.
- 로컬 재현에서 9월 응답 처리 후 8월 응답을 완료시키자 최종 데이터가 8월로 바뀌었다. 선택한 월/직원과 표시 데이터가 어긋날 수 있다.
- 개선: 요청 키와 현재 선택을 비교하거나 요청 세대 번호를 사용해 최신 응답만 반영한다. 취소 처리와 로딩 상태도 같은 요청 단위로 관리한다.

### 6. [P2] 월별 캐시가 만료되지 않고 새로고침도 해당 캐시를 갱신하지 않음

- 근거: `src/hooks/useDashboardData.js:168`, `:214`, `:429`; `src/components/dashboard/DashboardShell.js:259`, `:305`.
- 월별/휴가 캐시에는 만료 시간이 없고, 캐시가 있으면 서버를 재조회하지 않는다. 주기 갱신과 상단 새로고침은 오늘 데이터만 요청한다.
- 다른 관리자가 수정하거나 동기화 작업이 새 기록을 반영해도 월별 화면은 오래된 값을 유지할 수 있다. 일부 저장 경로의 `refreshAllData`/`refreshEmployeeData`는 갱신하지만 외부 변경을 해결하지는 못한다.
- 로컬 하네스에서도 같은 월 재조회 시 네트워크 호출이 0회였다.
- 개선: 조회 키별 만료/재검증 정책을 두고, 새로고침은 현재 화면의 데이터까지 갱신한다. 포커스 복귀 시 갱신과 진행 중 요청 중복 방지도 함께 설계한다.

### 7. [P2] Refresh token을 저장하지만 갱신에 사용하지 않음

- 근거: `src/app/api/auth/login/route.js:170`, `src/lib/auth.js:23`.
- 로그인은 access/refresh token 쿠키를 7일 동안 저장하지만, 검증은 기존 access token만 확인한다. `src` 검색에서 refresh token을 소비하거나 `refreshSession`을 호출하는 경로가 없다.
- access token이 만료되면 쿠키가 남아 있어도 로그인이 풀린다. 정확한 만료 시점은 인증 서버 설정에 따라 달라진다.
- 개선: 서버 측 토큰 갱신 및 쿠키 교체 경로를 추가하고, 갱신 실패 시 일관되게 로그아웃 처리한다.

### 8. [P2] 실패 시 갱신 간격 증가 로직이 실행되지 않음

- 근거: `src/hooks/useDashboardData.js:154`, `:246`.
- `fetchTodayData`가 예외를 내부에서 잡고 정상 종료하므로 호출자의 catch로 실패가 전달되지 않는다. HTTP 실패도 성공 여부를 반환하지 않는다.
- 따라서 스케줄러는 실패 후에도 `getNextRefreshDelay(true, delay)`를 호출한다. 기존 간격 계산 함수 테스트는 통과하지만 실제 연결은 잘못되어 있다.
- 로컬 하네스에서 fetch가 예외를 던져도 호출자 Promise가 reject되지 않음을 확인했다.
- 개선: 성공 여부를 반환해 갱신 간격에 반영하거나 예외를 전파한다. 함수 단위뿐 아니라 실패 응답과 스케줄러 연결을 테스트한다.

## 성능·유지보수 개선

### 9. [P2] 독립된 DB 조회를 순차 실행하고 전체 설정을 반복 조회함

- 근거: `src/app/api/attendance/route.js:107`, `:121`, `:124`, `:125`; `src/lib/supabaseDb.js:618`, `:1149`.
- 근태 데이터 → 직원 일정 → 초과근무 설정 → 직원별 초과근무 기간을 차례로 기다린다. 각 조회는 이전 조회의 결과를 입력으로 사용하지 않는다.
- 직원 한 명 조회에서도 일정과 초과근무 기간을 전체 조회하며, 프런트는 전체 월 조회 시 앞뒤 월도 미리 불러온다. 동일 설정 조회 비용이 반복된다.
- 개선: 권한 범위를 확정한 후 독립 조회를 병렬화하고, 직원별 설정은 허용 사번으로 범위를 제한한다. 공용 설정 캐시는 변경 시 무효화 정책과 함께 도입한다. 실제 개선 폭은 응답 시간·조회 건수 계측 후 판단한다.
